# Чеклист готовности к продакшену

Что уже сделано в коде, что настраивается один раз в внешних сервисах, и что
осознанно не входит в этот MVP.

## 1. Секреты и переменные окружения

- В коде фронтенда нет ничего, кроме `EXPO_PUBLIC_SUPABASE_URL` и
  `EXPO_PUBLIC_SUPABASE_ANON_KEY` (см. `.env.example`) — это публичные
  значения по дизайну Supabase, доступ к данным ограничивает RLS, а не
  секретность ключа.
- **Никогда** не добавляйте `service_role` ключ в приложение — он даёт полный
  доступ в обход RLS. Он нужен только для операций из доверенной среды
  (SQL Editor, серверный скрипт байера/админки — этапы 4–5 `PROJECT_PLAN.md`).
- `.env` в `.gitignore` — реальные ключи никогда не должны попасть в git.
- Для сборки через EAS переменные задаются в `eas.json` / EAS Secrets, а не
  хардкодятся.

## 2. Supabase: база данных и права доступа

- Схема (`supabase/schema.sql`) и сид (`supabase/seed.sql`) покрывают:
  каталог (`products`), сток по размерам (`product_variants`), избранное,
  корзину, заказы (`orders`), справочник доставки (`shipping_destinations`).
- RLS включён на всех таблицах:
  - `products`, `product_variants`, `shipping_destinations` — публичное
    чтение, запись только сервисной ролью (Table Editor).
  - `favorites`, `cart_items` — пользователь управляет только своими рядами.
  - `orders` — пользователь может **создавать и читать** только свои заказы;
    менять статус, трек-номер и т.д. может только оператор (сервисная роль).
    Это осознанное ограничение: до появления кабинета байера (этап 4)
    операции со статусом заказа — ручные, через Table Editor.
- Сток списывается атомарно триггером `decrement_variant_stock` при вставке
  заказа — оversell на уровне гонки запросов невозможен.
- **Обязательно перед запуском**: включить Anonymous Sign-Ins в Authentication
  → Providers (без этого корзина/избранное/заказы не будут сохраняться).
- HTTPS обеспечивается Supabase по умолчанию — отдельно настраивать не нужно.

## 3. Управление каталогом без кода

Полноценной админки нет — это осознанно отложено до этапа 5 (`PROJECT_PLAN.md`).
Пока используется **Supabase Table Editor**:

1. Открыть Table Editor → `products` → добавить строку (все поля соответствуют
   `Product` из `src/types/product.ts`, `images` — массив URL).
2. Для каждого продаваемого размера добавить строку в `product_variants`
   (`product_id`, `size`, `stock`) — без неё оформить заказ на этот размер
   нельзя (это защита от продажи того, чего нет).
3. Правки в `shipping_destinations` меняют доставку сразу во всех новых
   заказах (на уже созданные заказы не влияют — там хранится снимок).

Изображения сейчас — произвольные URL (плейсхолдеры picsum.photos в демо-
данных). Для реальных фото рекомендуется завести бакет в Supabase Storage —
это не требует изменений в коде, только вставки итогового URL в `images`.

## 4. Мобильный UX

- Изображения — через `expo-image` (кеширование на диск/в памяти, плавный
  fade-in) вместо обычного `Image` из React Native.
- Состояния загрузки: полноэкранный спиннер, пока грузятся каталог/доставка/
  сессия (`app/_layout.tsx`); индивидуальные экраны используют `EmptyState`
  для пустых списков (избранное, корзина, заказы, поиск без результатов).
- Ошибки: `ErrorBoundary` ловит краши рендера (аналог 500-страницы для
  мобильного приложения — сервера, который бы отдал HTML-страницу ошибки,
  здесь нет). `app/+not-found.tsx` — экран для несуществующего маршрута
  (аналог 404). Ошибки бэкенда при оформлении заказа (например, размер
  закончился) показываются пользователю через `Alert`, а не проглатываются.
- Раскладка построена на flex/gap/процентах — проверено на ширинах от 320px;
  два столбца каталога и карточки не переполняются на маленьких экранах.

## 5. Логи и аналитика

- `src/lib/logger.ts` и `src/lib/analytics.ts` — это **точки интеграции**,
  а не готовые сервисы: сейчас они только пишут в консоль в dev-режиме.
- Размечены ключевые события: `view_product`, `add_to_cart`,
  `begin_checkout`, `purchase` (см. вызовы `track(...)` в
  `src/store/AppStateContext.tsx`, `app/product/[id].tsx`, `app/checkout.tsx`).
- Перед реальным релизом: подключить реального поставщика аналитики
  (PostHog / Amplitude / Firebase Analytics) внутри `track()` и краш-репортинг
  (Sentry/Bugsnag) — инициализировать в `app/_layout.tsx`, пробрасывать туда
  же ошибки из `ErrorBoundary` и необработанные promise rejections.

## 6. SEO / Open Graph / favicon

Это нативное мобильное приложение, а не сайт — большинство «SEO»-требований
к нему не применимы напрямую:

- **Favicon** — есть, `app.json` → `web.favicon` (используется только если
  вы соберёте `expo export --platform web`, например для лендинга).
- **Open Graph / meta-теги** — добавлены в `app/+html.tsx`, тоже только для
  web-экспорта (превью ссылки в мессенджерах/соцсетях).
- «SEO» для самого приложения — это грамотно заполненные название, описание,
  ключевые слова и скриншоты в App Store Connect / Google Play Console при
  публикации (этап 10 `PROJECT_PLAN.md`), это делается там, а не в коде.

## 7. Международная доставка из Кореи

- `shipping_destinations` — Казахстан, Россия, Кыргызстан, Узбекистан и
  пример «остального мира» (Германия), с ценой, сроком и текстом про
  таможню.
- **Цены, сроки и пороги беспошлинного ввоза в сидах — демонстрационные
  оценки.** Перед реальным запуском обязательно согласовать актуальные
  тарифы с логистическим партнёром и актуальные пороги/ставки — с
  профильным юристом/брокером (правила меняются, дублировать их в коде
  без проверки нельзя).
- Заказ хранит снимок доставки (`shipping_country`, `shipping_cost`,
  `estimated_delivery_min/max_days`) и `tracking_number` — трек-номер пока
  проставляется вручную оператором в Table Editor; интеграция с реальным
  API перевозчика — будущий этап.

## 8. Возвраты

Сознательно не реализованы в этом MVP — по прямому запросу. Статус
`cancelled` покрывает только отмену заявки байером до покупки.

- [ ] Подключить реальный сервис аналитики и краш-репортинга.
- [ ] Согласовать реальные тарифы/сроки доставки и таможенные пороги.
- [ ] Настроить EAS Build/Submit, пройти модерацию сторов (этап 10).
